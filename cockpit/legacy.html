Sign in

Analytics reads are gated behind the admin Supabase account — the same credentials as the control panel.

From 1.9.5 this page reads TWO populations, and every tile says which one it is on its face. all installs = anonymous installs (anon:<iid>, from the funnel: channel) ∪ signed-in accounts — activity, activation, reliability, adoption, features. signed-in = accounts only, kept where a number structurally needs a session id, device context, a uid or a server table — session length, the per-user table, referrals, the identity rail, roster totals, feedback, watch-sync, write-path health. Who owns which number: PostHog owns installs, activation, engagement and retention for ALL installs and is the only PERSON-merged view; App Store Connect owns downloads; this page owns the signed-in roster, referrals, server-write health and per-user detail — and, from 1.9.5, an install-level read of its own. ⚠️ The backend deliberately cannot join an install to the account it later creates, so an all-time unique count is installs + accounts and a person who signed in may be counted in both; a daily or weekly active count overlaps on at most the single day of that sign-in. ⚠️ Complete only for installs on 1.9.5+ — an anonymous install on an earlier build wrote only the five pre-sign-in events, so every RATE restricts its anonymous denominator to v >= 1.9.5 while every COUNT includes them all. The Install → sign-in card is the per-install funnel; Write failures is the one mixed tile. Read a flat line here beside PostHog’s session_state split before calling it churn.

Do they reach value?

Activation funnel

Per ACTOR; each step is a subset of the previous. "Came back" = saw a score AND has ≥1 event on a later IST day. Left = all-time, right = actors first seen in the last 30 days. ALL INSTALLS from 1.9.5 — this is the funnel the Sep-16 misreading was really about: HealthKit grant and the first score happen BEFORE any sign-in, so a signed-in-only funnel had the sign-in as its top step and could not see activation at all. ⛔ The base excludes anonymous installs on builds ≤ 1.9.4: they cannot emit score_visible, so counting them would print an activation collapse caused by a build rather than by the product. Installs + accounts may double-count one person.
⚠️ THE OLD NOTE HERE SAID THESE STEPS COULD NEVER BE ADDED, AND 1.9.5 RETIRES THAT CLAIM. It was true of the events table: healthkit_authorized and score_computed latch once per install and fire during the anonymous phase, so a spent latch never reaches a uid-keyed row — sign-in does not backfill them. What changed is that the anonymous channel now carries them, keyed by install, so the grant and first-score steps are readable from THIS page for any install on 1.9.5+. PostHog remains the authority for the PERSON-merged view (this page cannot join an install to the account it later creates) and for installs on earlier builds.

Sign-in health — the step before the funnel

From sign_in, which fires at most once per successful sign-in (before 1.9.1: at most once per install). Counted per user on their BEST outcome: someone who hit an error and then signed in is a success, not a failure. From v1.9.1 a real error carries its cause — failure:error:<token>; rows from earlier builds say only failure:error and are counted as cause not recorded, never guessed into a cause. Cancelled is not a defect — it is someone closing Apple's sheet, and an app with zero cancels would be one that had stopped letting people leave.
⛔ THIS TILE CANNOT SEE A FIRST-INSTALL FAILURE, AND THAT IS STRUCTURAL. A failed attempt never writes vitalscore.appleUserID, so SupabaseService's uid-guard drops the event before it reaches this table — by design, since the row has no user to belong to. Everything below therefore reads: successes, cancels/errors from users who already had a session (a re-sign-in), and nothing else. PostHog is the authority for first-install failures (CEO · Sign-in health, prefix-match the payload). An empty error split here means "not visible from this source", never "no failures" — which is exactly what the last tile is for. From v1.9.1 a first-install failure is no longer merely dropped: it is written, per attempt, to the anonymous funnel: channel and counted on the Install → sign-in card below; the last tile here keeps reading the older day-latched log_event_no_uid signal, which pre-1.9.1 builds still emit. Also from 1.9.1 the door can be offered many times per install — sign_in_offered counts RENDERS of the sheet, from any of its four surfaces — while sign_in stays "at most once per successful sign-in", so offers and successes are not the same unit; PostHog owns the offer → success conversion by src. Signed-in users only: everything on this card is a row with a uid.

Install → sign-in — the dark stretch, lit (last 30 days)

⛔ WHY THIS CARD EXISTS (Aug 18 2026): App Store Connect counted 63 first-time downloads in 30 days; this dashboard counted 11 new signed-in users — 10 in July, one since Aug 1. Nothing could say where the other 52 went, because the app's first event of any kind was sign_in, fired only after Apple returned a credential. From v1.9.1 the app emits metadata-only events before any user id exists — app_first_launch (once per install), sign_in_offered (every render of the sign-in door, src:<profile|referral|feedback|promo>|first:<bool>), sign_in_tapped (every tap), session_state mode:anonymous (once a day per install) — and routes them, together with a failed sign_in, to the anonymous funnel: channel in app_logs: one row per event, keyed by a random per-install id (iid), never a user id. The success step is read from events (a success has a uid by then).
⛔ THE WALL STEP NO LONGER EXISTS (anonymous-first, 1.9.1). From 1.9.1 the app works without an account — launch → onboarding → HealthKit → Home, no sign-in — and Sign in with Apple is a door reached from Profile → Account, the Referral page, the Feedback form or a sign_in promo. So "below Installs" on the offered tile is the normal shape, not a bounce; the gap that matters is offered → tapped → success, per src. first: now means "this install has never completed a sign-in" (it used to mean never completed onboarding).
The definition, end to end: install [App Store Connect → App Analytics → Units, manual — no system we operate can see a download] → first launch [PostHog anonymous person · funnel:app_first_launch] → HealthKit → score visible [PostHog only, per install — anonymous, so nothing here] → offered sign-in [funnel:sign_in_offered, the door, per src] → tapped Sign in with Apple [funnel:sign_in_tapped] → signed in [events.sign_in = success] / failed [funnel:sign_in, per attempt]. Beside it, not in it: anonymous installs active [funnel:session_state mode:anonymous, 7d / 30d].
⚠️ What this card can and cannot see. Rows only arrive from builds carrying v1.9.1+, so every step reads zero until that build is the store build — a zero here is "not measured yet", not "nobody installed". Rows with build 1 are local simulator builds and are excluded. Counted per install (distinct iid), so three launches before a tap are one prospect. A handful of early-1.9.1 TestFlight rows still say funnel:sign_in_screen_shown (the wall's impression); they are counted as OFFERED and shown apart as "wall". A funnel row that fails to send is not retried; PostHog's copy is queued and retried and is the authoritative count — the founder's PostHog insights are written out in the note below.

Glance surfaces — widgets & watch

From the once-a-day widget_state / watch_state events (ship in 1.8.1). Each user's latest reading in the last 7 IST days counts once — these describe a device's state, not an action, so counting events would just count app opens. Denominators are users who reported, never the whole roster: a phone that cannot enumerate widgets, or whose watch session had not activated, sends nothing at all rather than a fabricated zero. The trailing tile is different on purpose: watch_open (Watch v2 Phase 0, ships in 1.9.1) is a genuine ACTION — the watch's own daily heartbeat — so it counts DISTINCT REPORTING DAYS, not a latest snapshot, and completes the funnel the other two stop short of: paired → app installed → app opened. This is the ≥14-day reading feature.watchInput may not flip on without. ALL INSTALLS from 1.9.5 — widgets and watches belong to INSTALLS, so this card was the clearest case of a fleet question getting a signed-in answer. Its kill criterion is written as "20% of installs" and can now be read off the right denominator. Anonymous installs on builds ≤ 1.9.4 never sent these events and are excluded from the reporting denominators rather than counted as non-adopters.

Appearance — which mode the fleet rests on

From the once-a-day appearance_state event (ships in 1.9, and is sent only while feature.lightMode is on — with the flag off there is no picker, so an empty tile means "not measured", never "everyone chose dark"). Each user's latest reading in the last 7 IST days counts once: this is a resting preference, not an action. The companion event appearance_set records the changes; this one records the state, which is the only way to see the actors who never touched it. ALL INSTALLS from 1.9.5 — the picker is offered to every install and, from this build, reported by every install, so the light-mode demand signal stops being a floor drawn from a self-selected minority.

Identity rail — how much of the fleet is server-verified

⛔ Signed-in users only, and structurally — not an omission from the all-installs train. identity_state describes whether a SIGNED-IN session was exchanged for a Supabase one; an anonymous install has no identity to verify and nothing to report, so the signed-in set is the complete and correct population here. ⚠️ What still holds: the anon-policy drop this card gates would break every install still writing as anon, and that population is invisible here by construction — read the DAU/WAU tiles and PostHog's session_state split before acting on any share below. From the once-a-day identity_state event and the per-sign-in identity_exchange (both ship in 1.9.1). Each user's latest state in the last 7 IST days counts once. This is the only observable the identity rail has — the release has no user-facing surface, so without this tile "did it land?" could only be answered by noticing that something else broke. Two things depend on the verified share: when the anon INSERT/UPDATE policies can be dropped (identity_rail.sql §9), and whether feature.referralRewards may ever be enabled. Anon is not a failure — an existing session cannot be upgraded silently (Apple issues a token only on a fresh authorization), so users convert as they re-sign-in. Exchange failures are.

Is the data healthy?

Sync health IS measurable now — the Jul 16 instrumentation round added metadata-only healthkit_authorized / score_computed / sync_completed / sync_failed events, so these tiles read real sync outcomes without a single health value leaving the phone. Every reliability tile in this section reads ALL INSTALLS from 1.9.5, with its anonymous denominator restricted to v >= 1.9.5 so an install that structurally could not report is never counted as having declined to. The session family (median session, sessions, events per active), watch-sync and feedback stay signed-in — each names its structural reason on its own tooltip. Write failures is mixed by nature (app_logs accepts a NULL user id). A percentage over a handful of actors still moves by tens of points on one bad week — read the counts.
